# IC Entropy

Reusable IC entropy acquisition for IcyDB, Canic, Auth and other consumers.
Platform Runtime supplies IC acquisition. The same crate owns the allocation-free
`Generator` and `SeedPool` modules, using upstream ChaCha20 for expansion.
Timers, metrics and logging are optional; it has no consumer-framework dependency.

The default selection provides `fresh_seed().await`: one bounded-wait management
`raw_rand` request, with no attached cycles, no cached result and no automatic
retry. Only one request may be outstanding. Call it after the relevant decision
commitment when fresh-after-commitment randomness is required.

## Runtime compatibility

The crate requires Platform Runtime 0.23.22 or a compatible 0.23 patch;
buffered builds require Timers 0.46.3 or a compatible 0.46 patch.
The workspace lockfiles select exact supplier versions.
Canister hosts with direct Runtime or Timers dependencies must use the matching
generations so the complete canister retains one executor and its exact guard.
Runtime's `raw-rand` operation owns request construction, transport and Protocol
reply validation. The crate retains replicated-execution admission, single-flight
custody, lifecycle fencing and the distinction between transport and framing errors.
Timers 0.46 requires the host to settle accepted work before upgrading, or use
a separately qualified reconciliation procedure. Reconstruction creates fresh
volatile state; it does not reconcile uncertain business effects.
Stop the canister, wait until its status is Stopped, upgrade, then start it.
Runtime callbacks and suspended futures are heap-local and must drain first.

## Background pool

Enable `buffered` on the consuming package's `ic-entropy` dependency.

The host calls `ic_entropy::reconstruct()` synchronously after restoring its
runtime during init and post-upgrade. It registers one retained IC Timers watchdog
(`ic-entropy/buffer/refill`) which makes background `raw_rand` calls until 256
independent 32-byte seeds are available (8 KiB of seed storage). Capacity is fixed.
Consumers can draw as soon as a seed arrives; they need not wait for a full pool.
Linking the crate alone starts nothing.
The host must compose this into its existing lifecycle owner; this crate exports
no canister endpoints or lifecycle entrypoints.

```rust,ignore
// Call from the existing synchronous host lifecycle participant.
fn restore_entropy() {
    ic_entropy::reconstruct().expect("entropy timer reconstruction failed");
}

```

`take_seed()` consumes a buffered seed exactly once. It can return `NotReady`
before the first refill and `Exhausted` when no replacement seed is available.
Buffered seeds and generated bytes do not carry fresh-after-commitment guarantees.

Successful refills are at least one second apart, so filling an empty pool takes
roughly four minutes or longer. A full pool idles; draws resume
refill demand. Failures back off for 1/2/4/8/16/32/60 seconds and pause after eight
consecutive failures. `retry_refill()` explicitly reopens the failure budget
without resetting an admitted generator. `status()` exposes readiness, pool
occupancy, remaining draw budget and the last typed error, but never seed bytes.
Status is query-safe; acquisition and draws require replicated Wasm execution.
Platform Runtime and ChaCha20 are normal dependencies. Timers is selected only
by `buffered`.

## Consumer-owned expansion

Each consumer owns its generator and chooses an output-byte budget when taking a
seed. Use the local generator API; no shared expansion setting or preset enum is
required. Call seed acquisition from an admitted update context:

```rust,no_run
# #[cfg(feature = "buffered")]
fn new_consumer_generator(
    byte_budget: u64,
) -> Result<ic_entropy::Generator, ic_entropy::Error> {
    let seed = ic_entropy::take_seed()?;

    Ok(ic_entropy::Generator::from_seed(seed, byte_budget))
}
```

Retain the returned generator in that consumer's volatile state. Its
`fill_bytes()` and `next_u128()` calls spend only its own budget. On exhaustion,
take a new seed and call `generator.reseed(seed, byte_budget)`; if acquisition
fails, leave the existing generator unchanged and retry later. Do not create a
new generator for every small draw or share a seed between consumers.

For example, a 64 KiB budget gives a 2,048:1 output-to-seed byte ratio; a 1 MiB
budget gives 32,768:1. These are operational reseeding limits, not entropy
multipliers or security ratings. Expansion does not increase the seed's entropy.
There is no fixed total output allowance for the pool: it depends on each
consumer's chosen budgets and direct seed consumption.

The shared `fill_bytes()` convenience function uses a shared stream
with a fixed 64 KiB budget per seed and a 1 KiB per-call limit. Use the
consumer-owned generator above when consumers need independent budgets.
`status().remaining_bytes` describes only that shared convenience stream; inspect
each owned generator with `remaining_bytes()` instead. Owned generators do not
enforce IC execution admission or the shared API's per-call limit; the consumer owns
those bounds.

### Complete host component

The [consumer-owned example](examples/consumer_owned.rs) retains two generators
with 2,000-byte and 20,000-byte budgets. It is a compile-checked library example
to integrate into an existing host, not a standalone canister or a native entropy
source. It introduces no endpoint or second lifecycle owner.

- Call its `reconstruct()` from the host's synchronous lifecycle participant,
  after restoring the complete timer provider. Seeds arrive asynchronously.
- In an update handler, use `fill_bytes(Consumer::Small, &mut [0; 8])` or
  `fill_bytes(Consumer::Large, &mut [0; 16])`. Subsequent calls retain each stream.
  Query draws refuse even when a generator already has available bytes.
- On insufficient budget it takes a new seed before reseeding. If acquisition
  fails, it returns the typed error without changing the destination or the old
  stream. Defer the operation or retry later; successful output is never refunded.
- Call its `suspend()` before snapshot/shutdown and handle errors before
  proceeding. It discards both owned generators before suspending acquisition.
- Use its `remaining_bytes(consumer)` for query-safe per-consumer observation.

Compile it for the IC with:

```sh
cargo check --locked -p ic-entropy --example consumer_owned \
  --features buffered --target wasm32-unknown-unknown
```

The regular lint target checks the native example and the Wasm check target
checks its IC admission path. Native draws deliberately return `NonReplicated`.

## Operational metrics

Enable the optional `metrics` feature to record into fixed `ic-metrics` counters
and bounded latency histograms. It works with fresh-only or buffered acquisition
and does not enable buffering or Timers' own metrics feature. No caller labels,
seed contents or generated bytes are retained. Direct generator and pool
operations do not record host observations.

Hosts can retain an `Rc<MetricsStorage>` beside their other metric sources,
following Timers' shared-storage pattern. Bind it before acquisition starts:

```rust,no_run
# #[cfg(feature = "metrics")]
# fn bind_entropy_metrics() -> Result<(), ic_entropy::Error> {
use ic_entropy::{MetricsStorage, initialize_with_metrics};
use std::rc::Rc;

let entropy_metrics = Rc::new(MetricsStorage::default());
initialize_with_metrics(Rc::clone(&entropy_metrics))?;
// Retain entropy_metrics in host state and project this snapshot for reporting.
let snapshot = entropy_metrics.snapshot();
assert_eq!(snapshot.fresh.attempts.total(), 0);
# Ok(())
# }
```

For a Canic host, the corresponding lifecycle integration is:

```rust,ignore
struct EntropySource;
impl canic::metrics::store::Source for EntropySource {
    type Storage = ic_entropy::MetricsStorage;
}

// Host lifecycle code, before entropy reconstruction or fresh requests:
ic_entropy::initialize_with_metrics(
    canic::metrics::store::open::<EntropySource>(),
)?;
// The reporting adapter reads store::get::<EntropySource>().map(|s| s.snapshot()).
```

Canic owns projecting those recorder values into its report DTO and shared
endpoint. Entropy has no Canic dependency. Preserve each counter's wide total and
overflow flag when projecting it; histogram bounds and counts are available on
`latency_ns`. Scheduler delivery diagnostics remain Timers' responsibility.

`initialize_with_metrics` starts no entropy or timer work. Repeating the same Rc
is idempotent; a different store returns `Busy`. Without explicit binding, the
first recorded operation selects private storage. `metrics()` reads the bound
snapshot without allocation and returns `None` before storage selection.

Counters accumulate for the heap incarnation. Suspension, reconstruction and
retry do not clear them. There is no in-place reset or persistence API; a normal
upgrade uses fresh host storage. The host owns lifetime labels and report/delta
windows, as with Timers. Query and native refusals create no observations.
Observations follow IC message rollback: a trap can roll back that message's
counter updates. They are diagnostics, not a durable log of external effects.

Fresh calls and background source calls have separate attempt, success, failure
and cancellation counters. Attempts begin on first poll; never-polled futures
are absent. Busy and disabled refusals count as failures but add no latency
sample. Dropped polled calls count as cancellations exactly once, without a
latency sample. Other completed calls measure observed elapsed nanoseconds from
first poll to completion, including message/scheduling delays; these are not IC
instruction or cycle measurements. Unavailable/backward clocks are counted
separately rather than recorded as zero latency.

Buffered metrics count pool seeds consumed, successful shared-generator bytes,
replicated draw/take refusals, automatic retries, failure-budget pauses, recovery
from nonzero failure streaks and explicit retry-budget resets. Stale refill
completions remain acquisition outcomes, but cannot change current-generation
retry/pause/recovery counters. Read current
occupancy, remaining budget and demand from the existing `status()` projection.
Expansion by a consumer-owned generator remains outside the shared API's
measurement boundary. Observations never authorize draws, source replay or
timer retries.

## Operational logging

Enable optional `logging` independently of `metrics` and `buffered`. Entropy
forwards fixed messages to a host-owned sink that accepts `ic_logging::Level`
from `ic-logging` 0.26. Without a configured sink, logging does nothing.
Direct generator and pool operations emit no log events.

For a Canic host using Logging 0.26, bind its shared logger during
synchronous lifecycle setup, before entropy reconstruction or fresh acquisition:

```rust,ignore
canic::logging::initialize();
ic_entropy::set_log_sink(Some(canic::logging::record))?;
```

Other hosts provide a `LogSink` function with the same signature and append to
an `ic_logging::Log`. The host owns timestamps, bounds, retention, persistence,
access control and reporting. It also handles append refusals. The sink must
return normally and avoid reentering mutating Entropy operations; it may read
`status()`. A sink panic can trap the calling message. No entropy state borrow
is held while invoking it.

`set_log_sink(None)` disables forwarding. Replacing or rebinding a sink never
clears host log storage. Setup requires replicated execution, and a fresh heap
needs a new binding after upgrade. Suspension and reconstruction retain the
binding in the current heap.

Info events cover suspension, fresh-request resumption, buffer reconstruction,
explicit refill retry and recovery from a nonzero failure streak. Transport,
malformed-reply and scheduling failures, and exhaustion of the eight-failure
refill budget are Warn events. Stale completions emit Debug. Source contention,
disabled refusals, routine successful acquisitions and draws stay quiet.
The source is always `ic-entropy`; messages contain no seeds, generated bytes,
caller labels or raw external error text. Logging follows IC message rollback
and remains diagnostic; it never authorizes retries or entropy consumption.

## Lifecycle and consumer policy

All entropy state is volatile. Call `suspend()` before a supported snapshot or
shutdown to invalidate pending replies, discard buffered seeds and stream state,
and cancel refill. After restoration, reconstruct the whole host/shared timer
provider before calling `reconstruct()`. This crate cannot safely resume a
captured shared-provider heap; arbitrary snapshot load is not supported merely
by linking this crate. Fresh-only hosts call `resume_fresh_requests()` after
restoring their execution context. Late replies cannot populate a replacement
lifecycle instance.

The host must also discard every consumer-owned generator on suspension, restart
or restore. Adapter lifecycle calls cannot invalidate generators already handed
to consumers. Reacquire separate seeds before resuming their draws.

Consumers own admission and usage policy: IcyDB's once-only boot seed acceptance,
Auth's fresh challenges and application decisions remain downstream. Do not share
one seed between independent consumers or replace fresh requests with buffered
draws where timing is part of the protocol. Seeds are not confidential from subnet
operators; a local generator does not increase their entropy.

## Validation

Native model tests cover retries,
