# IC Entropy IC adapter

Reusable IC entropy acquisition for IcyDB, Canic, Auth and other consumers.
This package depends on Platform and optionally IC Timers and IC Entropy; it
has no dependency on those consumers.

The default selection provides `fresh_seed().await`: one bounded-wait management
`raw_rand` request, with no attached cycles, no cached result and no automatic
retry. Only one request may be outstanding. Call it after the relevant decision
commitment when fresh-after-commitment randomness is required.

## Background pool

Enable `buffered` in the consuming package. Inside this workspace:

```toml
[dependencies]
ic-entropy.workspace = true
ic-entropy-ic = { workspace = true, features = ["buffered"] }
```

The host calls `ic_entropy_ic::reconstruct()` synchronously after restoring its
runtime during init and post-upgrade. It registers one retained IC Timers watchdog
(`ic-entropy-ic/buffer/refill`) which makes background `raw_rand` calls until 256
independent 32-byte seeds are available (8 KiB of seed storage). Capacity is fixed.
Consumers can draw as soon as a seed arrives; they need not wait for a full pool.
Linking the crate alone starts nothing.
The host must compose this into its existing lifecycle owner; this crate exports
no canister endpoints or lifecycle entrypoints.

```rust,ignore
// Call from the existing synchronous host lifecycle participant.
fn restore_entropy() {
    ic_entropy_ic::reconstruct().expect("entropy timer reconstruction failed");
}

```

`take_seed()` consumes a buffered seed exactly once. It can return `NotReady`
before the first refill and `Exhausted` when no replacement seed is available.
Buffered seeds and generated bytes do not carry fresh-after-commitment guarantees.

Successful refills are at least one second apart, so filling an empty pool takes
roughly four minutes or longer. A full pool idles; draws resume
refill demand. Failures back off for 1/2/4/8/16/32/60 seconds and pause after eight
consecutive failures. `retry_refill()` explicitly reopens the failure budget
without resetting an admitted generator. `status()` exposes readiness, pool
occupancy, remaining draw budget and the last typed error, but never seed bytes.
Status is query-safe; acquisition and draws require replicated Wasm execution.
Fresh-only selection brings neither Timers nor ChaCha20 through this package.

## Consumer-owned expansion

Each consumer owns its generator and chooses an output-byte budget when taking a
seed. Use the existing core API; no shared expansion setting or preset enum is
required. Call seed acquisition from an admitted update context:

```rust,no_run
# #[cfg(feature = "buffered")]
fn new_consumer_generator(
    byte_budget: u64,
) -> Result<ic_entropy::Generator, ic_entropy_ic::Error> {
    let seed = ic_entropy_ic::take_seed()?;
    Ok(ic_entropy::Generator::from_seed(seed, byte_budget))
}
```

Retain the returned generator in that consumer's volatile state. Its
`fill_bytes()` and `next_u128()` calls spend only its own budget. On exhaustion,
take a new seed and call `generator.reseed(seed, byte_budget)`; if acquisition
fails, leave the existing generator unchanged and retry later. Do not create a
new generator for every small draw or share a seed between consumers.

For example, a 64 KiB budget gives a 2,048:1 output-to-seed byte ratio; a 1 MiB
budget gives 32,768:1. These are operational reseeding limits, not entropy
multipliers or security ratings. Expansion does not increase the seed's entropy.
There is no fixed total output allowance for the pool: it depends on each
consumer's chosen budgets and direct seed consumption.

The adapter's existing `fill_bytes()` convenience function uses a shared stream
with a fixed 64 KiB budget per seed and a 1 KiB per-call limit. Use the
consumer-owned core generator above when consumers need independent budgets.
`status().remaining_bytes` describes only that shared convenience stream; inspect
each owned generator with `remaining_bytes()` instead. Core generators do not
enforce IC execution admission or the adapter's per-call limit; the consumer owns
those bounds.

## Lifecycle and consumer policy

All entropy state is volatile. Call `suspend()` before a supported snapshot or
shutdown to invalidate pending replies, discard buffered seeds and stream state,
and cancel refill. After restoration, reconstruct the whole host/shared timer
provider before calling `reconstruct()`. One adapter cannot safely resume a
captured shared-provider heap; arbitrary snapshot load is not supported merely
by linking this crate. Fresh-only hosts call `resume_fresh_requests()` after
restoring their execution context. Late replies cannot populate a replacement
lifecycle instance.

The host must also discard every consumer-owned generator on suspension, restart
or restore. Adapter lifecycle calls cannot invalidate generators already handed
to consumers. Reacquire separate seeds before resuming their draws.

Consumers own admission and usage policy: IcyDB's once-only boot seed acceptance,
Auth's fresh challenges and application decisions remain downstream. Do not share
one seed between independent consumers or replace fresh requests with buffered
draws where timing is part of the protocol. Seeds are not confidential from subnet
operators; a local generator does not increase their entropy.

## Validation and provenance

The source was extracted from the local Canic adapter; the package includes
`PROVENANCE.md` and the retained MIT `LICENSE`. Native model tests cover retries,
cancellation, stale replies and bounded draws. The repository's separate
qualification workspace installs a standalone canister on PocketIC to check real
management randomness, background refill, query refusal, suspension and fresh-heap
upgrade/reinstall reconstruction. This does not establish arbitrary heap-snapshot
restore safety or downstream framework/database integration.
